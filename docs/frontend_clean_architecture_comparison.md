# フロントエンドの設計思想とクリーンアーキテクチャとの比較

本書は，本プロジェクトのフロントエンド（`frontend`）が，クリーンアーキテクチャの思想とどのように対応して設計されているかを解説するものである．

---

## 1. 結論：厳格なクリーンアーキテクチャではないが，思想は極めて近い

結論として，フロントエンドは「Domain」や「Use Case」といったフォルダ階層を厳密に分離したクリーンアーキテクチャではない．しかし，クリーンアーキテクチャの根本思想である **「関心の分離（UIの描画とビジネスロジック・通信の分離）」** は忠実に守られて構築されている．

---

## 2. クリーンアーキテクチャのレイヤーとの対応関係

フロントエンドの各要素は，クリーンアーキテクチャにおける以下の概念にマッピングすることができる．

| フロントエンドの構成要素         | クリーンアーキテクチャでの役割       | 具体的な役割の説明                                                                                                                 |
| :------------------------------- | :----------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------- |
| **① Components (`components/`)** | **View / Presenter (最外周)**        | 画面の表示とユーザー操作の受け付けのみに専念する．API通信の方法やデータの更新手順などは一切知らない．                              |
| **② Custom Hooks (`hooks/`)**    | **Use Cases / Controller (内側)**    | 「プロフィールを取得する」「バッジを獲得する」といった，画面ごとの操作手順（ユースケース）と状態を管理する．UIと通信層を仲介する． |
| **③ SWR / Fetcher (`lib/`)**     | **Gateways / Data Sources (最外周)** | ネットワーク通信（HTTP Fetch）を実行し，キャッシュを管理するデータソース層である．                                                 |
| **④ API Routes (`app/api/`)**    | **BFF (Backend For Frontend)**       | クライアントとバックエンドを繋ぐゲートウェイである．バックエンドのコントローラーを呼び出してデータを中継する．                     |

---

## 3. この「関心の分離」設計のメリット

1. **UIの変更が容易（見た目の差し替えやすさ）**：
   UIコンポーネントは，データがどのようにフェッチされているか（SWRか，通常のfetchか）を知る必要がない．カスタムフックから返されるデータ形式さえ一致していれば，見た目（CSSやHTML構造）を自由に変更できる．
2. **ロジックのテストが容易**：
   Reactの画面描画をおこなうことなく，カスタムフックのロジックやデバイス制御（カメラ起動など）のロジックだけを切り出して自動テスト（Vitest）を実行できる．
3. **コードの再利用性が高まる**：
   「プロフィールを取得・更新する」という同じロジックを，異なる複数のコンポーネントやページから，カスタムフック（`useProfile`）を呼び出すだけで使い回すことができる．
