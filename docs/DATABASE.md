# データベース設計仕様書

### システムのデータ整合性と永続性

すべてのデータは Supabase (PostgreSQL) によって管理され、タイムスタンプは日本時間 (JST) で処理・格納される。PostgreSQL のデフォルト値およびトリガーにより、挿入・更新時に自動的に `now() + interval '9 hours'` がセットされる。

実際のテーブル構築用 SQL や初期データの投入スクリプトについては、[DATABASE_SQL.md](./DATABASE_SQL.md) を参照すること。

---

## 1. テーブル: `badges`

AR 体験で使用されるデジタル標本のマスターデータである。

| カラム名 | 型 | Zod バリデーション | 説明 |
| :--- | :--- | :--- | :--- |
| `id` | UUID (PK) | `uuid()` | 作品の一意の識別子。 |
| `name` | String | `min(1)` | 作品の表示名。 |
| `target_index` | Integer | `int().min(0)` | AR マーカーのインデックス (0-5)。 |
| `model_url` | String | `url()` | AR 表示用の 3D モデル (.glb) パス。 |
| `image_url` | String | `url()` | 詳細表示用の 2D 画像 (.jpg) パス。 |
| `created_at` | Timestamp | `string().optional()` | 登録日時（日本時間 JST）。 |

---

## 2. テーブル: `user_badges`

ユーザーによる獲得記録のトランザクションログである。主要な冪等性ロジックを実装する。

| カラム名 | 型 | Zod バリデーション | 説明 |
| :--- | :--- | :--- | :--- |
| `user_id` | UUID (FK) | `string()` | profiles.id への参照。 |
| `badge_id` | UUID (FK) | `uuid()` | badges.id への参照。 |
| `acquired_at` | Timestamp | `string()` | 獲得時のタイムスタンプ（形式の差異を許容）。 |

### 制約事項

- **複合ユニーク制約 (`unique_user_badge`)**: `(user_id, badge_id)`
  - **目的**: 同一ユーザーによる同一バッジの重複獲得記録を防止する。
  - **動作**: データベースレベルで冪等性を担保し、アプリケーションレイヤーからの安全なリトライを可能にする。

## 4. クエリとインデックス

### インデックス戦略

- `user_badges.user_id` に対する B-tree インデックス：ユーザーの獲得履歴取得を最適化する。
- `badges.target_index` に対するインデックス：AR マーカー認識時の検索効率を向上させる。

### キャッシングおよび高負荷対策戦略

本システムでは、PostgreSQL の負荷軽減とレスポンス高速化のため、以下の多層キャッシング層を実装している。

1.  **クライアントサイド (SWR)**: `stale-while-revalidate` 戦略により、ブラウザ側でデータを保持しつつバックグラウンドで同期する。
2.  **エッジキャッシュ**: 3D モデル等の静的アセットに対し、CDN による強力なキャッシュを適用している。
3.  **Redis (Upstash) による API キャッシュ**:
    - **対象**: 管理者ダッシュボードの「グローバル統計データ」。
    - **仕組み**: 集計コストの高い統計クエリの結果を Redis に 5 分間（300 秒）保存する。
    - **効果**: 同時アクセス数が増加しても、PostgreSQL のリソースを消費せずにミリ秒単位のレスポンスを維持する。
